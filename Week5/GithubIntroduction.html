A complete first trip through GitHub

Hello World, step by step.

Build a tiny repository, make a change on a separate branch, discuss it in a pull request, and merge it. Each part below explains what you are doing, where to click, and what to check before moving on.

What you need: a GitHub account and a web browser. You do not need coding experience, Git installed, or a terminal.

What you will finish with: a hello-world repository whose README contains a change merged from your first pull request.

Your route: repository → branch → edit → commit → pull request → review → merge. Tick the checklist boxes as you complete each stage; they are saved in this browser.

Step 01 / Set up the project

Create a repository

A repository holds a project’s files and their change history. Imagine a project folder with a record of what changed. The README is usually the first page a visitor sees; it explains what the project is about. It is a Markdown file, so simple symbols can format headings and lists.

  1. Sign in to GitHub. In the top-right corner, open the + menu and choose New repository.
  2. Set Repository name to hello-world. If that name is already in use on your account, choose a recognisable variation such as hello-world-practice.
  3. Add a short Description saying this is your GitHub practice project.
  4. Choose Public if you are comfortable with anyone seeing this practice work, or Private if you want limited access. Do not put personal secrets in either kind of repository.
  5. Tick Add a README file. Leave the other options alone for now, then select Create repository.
Check the result: you should see your new repository’s Code page and a README.md file. The README gives the next steps a starting commit.
Step 02 / Work without changing the default yet

Create a branch

A branch is a separate line of work. Your new repository starts on a default branch, normally main. A new branch begins with the same files, so you can try changes without putting them on the default branch immediately. When your work is ready, you can merge it back.

  1. From your repository, select the Code tab if you are not already there.
  2. Above the list of files, open the branch dropdown. It probably says main; if yours has another name, use the name you see.
  3. Type readme-edits into the branch search field.
  4. Choose Create branch: readme-edits from main (or from the default branch shown on your screen).
Check the result: the dropdown now shows readme-edits, and the README still looks the same. The branches only become different when you edit one.
Step 03 / Save a change with a reason

Edit and commit the README

A commit records a change to your files. Its message should tell future readers what you changed or why. Because you are editing through GitHub’s website, you will not need a separate push command: the web edit is saved to the online repository when you commit it.

  1. While viewing readme-edits, open README.md.
  2. Click the pencil icon (or the edit option) near the top of the file.
  3. Add a short paragraph about yourself or your practice project. For example, write your own version of the following:
## What I am practising
I am learning how branches and pull requests work.
My first change is an update to this README.
  1. Select Commit changes. In the commit dialog, replace any generic message with a useful one, such as Describe my GitHub practice.
  2. Confirm with Commit changes again. Make sure the change is committed to your readme-edits branch.
  3. Read the file on readme-edits. Then switch to the default branch and look at the same file: your new paragraph should not be there yet. Switch back to readme-edits before continuing.
If you cannot see the change: check the branch name at the top of the file first. You may be looking at the default branch rather than the branch where you committed.
Step 04 / Show the change before accepting it

Open a pull request

A pull request (PR) proposes bringing the work from one branch into another. It offers a place to describe the change, inspect the diff (what was added or removed), and invite comments before merging. In this personal practice repository, you can review your own PR; in a shared project, another person might review it.

  1. Open the repository’s Pull requests tab, then choose New pull request.
  2. Set the base to your default branch (normally main) and the compare branch to readme-edits. Think: “bring changes from compare into base”.
  3. Look at the file diff before proceeding. Lines marked + or coloured green are additions; lines marked − or coloured red are removals. Check that the intended README edit is the only change.
  4. Choose Create pull request. Give it a useful title, such as Add a practice introduction to README, and briefly explain what you added and why.
  5. Choose Create pull request again to submit it. On the PR page, open Files changed and read the final diff.
Check the result: your PR is open, its title explains the change, and the diff shows the correct file. A review is more than clicking a button: ask whether the proposed change makes sense and whether it affects anything unexpected.
Step 05 / Bring the approved work together

Merge the pull request

Merging incorporates the branch’s committed change into the default branch. In a real team, you would usually wait for the required review and checks. Here you are practising on your own repository, so you can complete the merge after checking the diff.

  1. On the pull request page, select Merge pull request.
  2. Select Confirm merge. The PR should now show that it is merged and closed.
  3. Select Delete branch if offered. Deleting the finished practice branch does not erase the merged change from the default branch.
  4. Return to the Code tab and select your default branch. Open README.md and confirm that your paragraph appears there now.
If GitHub reports a conflict: do not click through blindly. A conflict means GitHub cannot combine some changes automatically; review what changed on each branch first. This simple exercise normally has no conflict.
Review / Explain your work

What happened, in order?

You made a project home, created a separate line of work, saved a named change, proposed it for review, and brought it into the default branch. A commit saved the edit on your branch; merging brought it into the default branch.

Explain it to a partner: What is the difference between a commit and a pull request? Why check the diff before merging? Where is your README edit after the branch is deleted?

Try again: create a new branch, add one more useful line to the README, commit it, and follow the PR workflow again. To learn more after this browser-only introduction, explore GitHub flow and Markdown basics.
